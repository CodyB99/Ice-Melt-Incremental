# Architecture and Product Decisions

Record decisions that materially change scope, dependencies, data schema, security, economy, or release behavior.

| Date | Decision | Reason | Consequences |
|---|---|---|---|
| 2026-08-02 | Use a small three-zone MVP | Launch and validate quickly | Later content must remain configuration-driven |
| 2026-08-02 | Use vanilla Roblox APIs for MVP | Reduce dependency and setup risk | Persistence/session safety must be tested carefully |
| 2026-08-02 | Server-authoritative melt rewards | Prevent simple remote exploitation | Client effects may be predicted but reconciled |
| 2026-08-02 | One Thaw prestige layer | Avoid progression bloat before retention data | Additional layers remain post-launch backlog |
| 2026-08-02 | Environment resolved once in `EnvironmentConfig`, never from `RunService:IsStudio()` at call sites | Phase 00 requires the mode to be explicit and production to be unreachable by accident | Production requires an allow-listed PlaceId and is rejected outright in Studio; unregistered places fall back to Test, never Production |
| 2026-08-02 | World skeleton built at runtime by the server, not hand-placed in Studio | Reproducible from source control, cannot drift from configuration, and matches the phase requirement for server-created runtime folders | Edit mode shows a bare place; the world only exists in Play. Builder is idempotent and versioned so layout changes rebuild rather than accumulate |
| 2026-08-02 | Foreign SpawnLocations disabled rather than destroyed at startup | The Baseplate template spawn sits inside the Backyard slab and would break onboarding | Change is reversible and logged; only `Hub/Spawn` is enabled |
| 2026-08-02 | Commit selene's generated `roblox.yml` instead of downloading it per machine | Norton 360's HTTPS interception makes selene's API-dump download fail with `UnknownIssuer`; rustls ignores the Windows certificate store | `selene src` runs offline everywhere. Regenerate only on a material Roblox API change, which needs Norton's web scanning paused once |
| 2026-08-02 | Run both `luau-lsp analyze` and `selene` as required checks | They catch different classes of defect: the typechecker found a union-narrowing bug, selene found duplicate `if`/`else` branches | `scripts/analyze.ps1` and `scripts/lint.ps1` both gate a phase, and both fail hard rather than warn |
| 2026-08-02 | Rojo serves on port 34873 | The default 34872 is permanently held by another project on this machine | Port pinned in `default.project.json`; the Rojo plugin must be set to 34873 or it will sync the wrong project |
| 2026-08-02 | `.gitattributes` pins `* text=auto eol=crlf` | `core.autocrlf` was guessing per file, so `.luau` was CRLF and everything else LF | Repository stores LF, working tree is CRLF, matching `stylua.toml` and PowerShell. All 46 mixed files normalised |
| 2026-08-02 | No client-invoked RemoteFunctions; all 14 remotes are RemoteEvents | A RemoteFunction invoked from a client parks a server thread until it returns, so a malicious client can stall server work just by calling one | Requests are fire-and-forget events; the server answers on `ActionResult` or `PlayerState`. Any future request/response pair must follow the same shape |
| 2026-08-02 | Remote schema is a closed list with enforced direction | "Server creates only expected remotes" has to be checkable, not a convention | `RemoteRegistry` destroys anything in the Remotes folder not in the schema, and both sides refuse to use a remote against its declared direction |
| 2026-08-02 | Added `ClientReady` and `ActionResult` beyond the kit's original remote list | The phase requires a safe handshake and a state-ready signal, and denials need a channel back to the client | A generic server→client *result* channel is safe; a generic client→server *command* channel is not, and `ConfigAudit` fails if one is ever added |
| 2026-08-02 | `Init` must not yield; detected rather than documented | A yield in `Init` silently reorders startup and reintroduces the race the two-phase lifecycle exists to remove | `Lifecycle` runs `Init` in a coroutine and reports any entry left suspended. Work that must wait belongs in `Start` |
| 2026-08-02 | Client handshake retries a bounded 4 times | `ClientReady` is an event, so firing it before the server connects its listener drops it silently and leaves the client with no state forever | Retry stops on first snapshot and warns if it gives up. The server treats `ClientReady` as idempotent and rate-limits it |
| 2026-08-02 | Union-typed config values go through typed constructors, not table literals | A string literal in a table widens to `string` and loses the union check, which `luau-lsp` rejected | `discovery()` in ContentConfig and `spec()` in RemoteNames; a typo like `"Mythic"` now fails to typecheck at the call site |
| 2026-08-02 | Every profile read and write goes through `UpdateAsync`, never Get/SetAsync | Only UpdateAsync makes the session-lock check and the write it guards a single transaction; with Get then Set, two servers can interleave and one silently wins | All storage goes through one `update(key, transform)` primitive. A transform returning nil aborts the write, which is how a lock conflict declines rather than clobbers |
| 2026-08-02 | A profile that fails to load results in a kick, never in default data | Handing out defaults and then autosaving writes them over a profile that is probably fine. A kick is recoverable; overwritten save data is not | Distinct messages for `Locked`, `Incompatible`, and `Failed`. The player is told their progress is safe |
| 2026-08-02 | A profile from a newer schema version aborts the load entirely | Refusing to migrate is not enough on its own: repair would still strip unknown fields and the next save would persist the stripped copy | `normalise` reports `tooNew` and `DataService` returns `Incompatible` without claiming the lock. Verified: version, Heat, and an unknown field all survived |
| 2026-08-02 | Studio session-lock identity is stable per place | `game.JobId` is empty in Studio, so a time-derived id made every play session look like a different server and locked the developer out of their own profile for the 150s timeout | A restarted Studio session reclaims its own lock immediately. Safe because Studio cannot reach production and profiles are keyed per user |
| 2026-08-02 | Session lock expires after 150s rather than being permanent | A crashed server never releases its lock; without expiry the player could never rejoin | Chosen to be well above the 30s heartbeat so a healthy server never looks stale, and low enough that a crash costs one short wait |
| 2026-08-02 | Client-facing state is an explicit allow-list, not a filtered profile | Filtering means remembering to strip each new secret field; an allow-list means a new field is private until someone deliberately publishes it | `buildSnapshot` names all 8 fields. Verified on the wire that ReceiptHistory, LifetimeHeat, RunHeat, RewardState, Settings, and Discoveries never leave the server |
| 2026-08-02 | Dev commands are a ServerStorage BindableFunction, not a remote | ServerStorage does not replicate, so the entry point is invisible to clients. A client-callable admin channel is exactly what the Phase 01 remote schema forbids | Reachable from the Studio command bar only, and not created at all when the environment is Production |
| 2026-08-02 | Studio falls back to a non-persistent in-memory store when API access is off, but a live server never does | Development must not be blocked by a Studio setting, but silently "saving" to memory on a live server would destroy real progress | The fallback warns loudly and `DataService.isPersistent()` reports it |
| 2026-08-02 | The melt payload carries only a sequence number | The server derives position, zone, stats, targets, damage, and reward from authoritative state. Validating a client-supplied target list costs more than computing the correct one, and accepting one means trusting a client to name its own targets | There is nothing in the payload to forge. Position comes from the server's copy of the HumanoidRootPart |
| 2026-08-02 | Cell parts are created once and never destroyed | Melting hides a cell and respawn restores it, so sustained play allocates nothing. Create/destroy per melt is the churn docs/02 forbids | Verified: 256 instances before, during, and after a heavy melt and respawn cycle |
| 2026-08-02 | Cells are found by grid index arithmetic, not by scanning | A regular grid means the cells inside a radius can be computed directly, so cost scales with radius rather than field size | Field dimensions must stay a regular grid. Irregular set pieces in Phase 05 need their own lookup rather than being mixed into this one |
| 2026-08-02 | Cell appearance updates only on a crack-stage boundary | Property writes replicate. Updating on every point of damage would flood the network to show a change no one can see | Four visible stages per cell |
| 2026-08-02 | Crits multiply reward, not damage | Scaling both would make Crit a second Power stat and double-dip against the balance curve in docs/03 | Crit is purely an economy stat |
| 2026-08-02 | The client suppresses pulses when far from every ice field | Ten remotes a second per player, forever, for guaranteed rejections is real waste at scale | Explicitly a bandwidth optimisation, not a security control. The server validates every pulse regardless, and the margin is the maximum possible radius so it can never suppress a pulse that would have succeeded |
| 2026-08-02 | Melt rejection reasons are echoed to the client in development only, throttled per reason | On a live server, telling a client exactly which validation it failed is free tuning information for an exploit. Unthrottled, a persistent condition buries the Output | One echo per reason per second, and none at all in Production |
| 2026-08-02 | First published place registered as **Test**, not Production | Publishing must never silently point a live server at production player data | `PRODUCTION_PLACE_IDS` stays empty until the owner explicitly promotes a place |
